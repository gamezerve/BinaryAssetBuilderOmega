# AudioFile XML and file-dependency identity proof

Date: October 4, 2026. This managed-only fixture reconstructs the actual current
core AudioFile InstanceHash independently of DocumentProcessor's orchestration.
It does not compile audio, execute reference/native DLLs, publish manifests, or
establish a stock Uprising InstanceHash match.

## Implementation and observed result

- `tests/fixtures/AudioFileIdentityPipeline.xsd` wraps the existing AudioFile
  harness with AssetDeclaration. Official EP1 types/includes remain unchanged.
- `AudioFileIdentitySmokeTest.Build` registers a private identity-only plugin and
  uses actual DocumentProcessor/SchemaSet/SessionCache with GenerateOutput=false.
  Every attempt gets fresh settings/cache and restores Settings.Current on exit.
- `Expected` independently validates the authored XML, captures the AudioFile
  serialization before normalization, folds 512-character text blocks, hashes
  owned WAV bytes, then combines a fixed capacity-padded dependency buffer.
- `IdentityOnlyPlugin` is test-local, denies production output and cache/document
  reuse, and throws from ProcessInstance. Tests assert the registry output/reuse
  gates. It is not installed in a production descriptor or diagnostic admission.

The owned WAV is 24,044 bytes: PCM16 mono, 48 kHz, 12,000 samples, from the existing
managed fixture generator. Current document version 23 and an explicitly test-only
ProcessingHash 52424849 produce InstanceHash **51490DA8**, equal to the actual core
result. Using the observed RA3 reference ProcessingHash 8FE79286 and document
version 11 in the offline reconstruction produces **2C240AF8** for these same
authored inputs. This latter value is not a reference-compiler execution result
and neither value is asserted as an original Uprising producer identity.

## Construction details verified

1. Official schema defaults, including PCQuality=75, enter XML before hashing.
2. The XML seed incorporates processor fingerprint and document version text.
3. Hashing occurs before File becomes a normalized absolute lowercase path and
   before TypeId injection. Authored filename spelling still affects the hash.
4. The WAV dependency hash starts with its file length and folds actual bytes.
   Fixtures are bounded below 1 MiB, so this proof covers one reader chunk only.
   An empty dependency preserves the zero length seed without folding a chunk.
5. The four-byte file hash is written little-endian at the beginning of a
   **256-byte** zero-padded buffer. Core hashes the backing capacity, not only the
   four logical bytes, and XORs that result with the XML hash. Tests distinguish
   the short-buffer alternative.
6. Instance metadata retains the logical `input.wav` dependency while the XML
   File attribute becomes the resolved absolute path. No runtime asset reference
   or import is generated by this FileReference.

Eight independently reconstructed fixtures cover baseline, repeated build in a
different directory, changed PCM byte, changed XML stream setting, changed
processor fingerprint, uppercase authored filename, length change and empty
dependency. A ninth fixture rejects missing WAV with FileNotFound, then succeeds
after adding the owned WAV with a fresh cache. Recovery is not a claim about a
long-lived cache or timestamp-preserving same-size edits; those have separate
existing cache tests.

Length-change and empty-file cases intentionally test dependency hashing, not
valid WAV input. They must still be rejected by the separate codec input profile
before any audio encoder invocation. No codec readiness follows from hash success.
XML serialization uses the current runtime's Encoding.Default; old .NET Framework
codepage equivalence and multi-chunk file hash compatibility remain unproven.
